QHARE Failure-Aware Decision Architecture

QHARE treats a UI failure as a diagnostic event first, not automatically as a broken locator.
AUTOMATION FAILURE → FAILURE CLASSIFIER
IS HEALING APPROPRIATE?

🔧 HEAL

Same logical element, changed representation
  • Attribute matching
  • Structural matching
  • Semantic matching
  • Accessibility signals
  • Historical matching
  • Confidence scoring

🔄 RECOVER

Locator is valid; runtime state is wrong
  • Wait / re-query / retry
  • DOM stability
  • Popup / modal recovery
  • Context / frame recovery
  • Navigation/state recovery
  • Retry original locator

🛑 DO NOT HEAL

Potential real product/system failure
  • Product defect
  • Auth / permission
  • Test data / business state
  • Backend / network
  • Wrong page
  • Unsafe / ambiguous action
POST-ACTION VALIDATION → Accept only when expected application behavior is verified; otherwise reject and preserve the original failure.

The Four QHARE Pillars

A simple executive story that can sit above the detailed technical model.

HEAL

Repair genuine element changes.

  • Attributes
  • DOM structure
  • Semantics
  • Accessibility
  • Context

RECOVER

Restore recoverable execution state.

  • Synchronization
  • Popup / overlay
  • Context
  • Navigation
  • Page state

PROTECT

Know when not to heal.

  • Product defects
  • Business failures
  • Auth / data
  • Backend
  • Unsafe actions

LEARN

Improve automation reliability.

  • Element history
  • Confidence
  • Telemetry
  • Flakiness
  • RCA

Presentation Closing

QHARE is not positioned as “another locator healer.” It is an orchestration layer for deciding when to heal, when to recover, when to preserve failure, and how to learn from every outcome.

Healenium is best presented as selector resilience. Healwright is best presented as AI locator resilience. QHARE’s differentiation is the broader failure-aware operating model: HEAL → RECOVER → PROTECT → LEARN.
