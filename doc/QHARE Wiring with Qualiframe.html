QHARE Wiring with Qualiframe

Step-by-step map of how QHARE (Qualiframe Adaptive Healing & Reliability Engine) is wired into this framework: config, exclusive provider switch, driver wrap, find-element intercept, heal/recover, and Reqnroll telemetry flush.

Overview 1. Config 2. Resolve 3. Scenario scope 4. Driver wrap 5. Native find 6. Heal 7. Recover 8. Telemetry End-to-end

Overview

QHARE is wired as an exclusive WebDriver wrapper. Page objects still call Selenium By locators. The factory wraps the real browser driver so a miss can go to the QHARE core. Healenium is never applied at the same time.

You do not change page objects, locators, waits, or step definitions to use QHARE. The wiring is config + factory wrap + Reqnroll hooks. The QHARE process itself is external; this repo only talks to Qhare:BaseUrl.

1. Flip the exclusive provider

In src/QualiFrame.Framework/Configuration/appsettings.json, two blocks matter: SelfHealing:Provider and Qhare. 

{
  "SelfHealing": {
    "Provider": "Qhare"
  },
  "Qhare": {
    "Enabled": true,
    "BaseUrl": "http://localhost:3000",
    "ProjectId": "qualiframe-selenium-c#",
    "Mode": "AUTO_HEAL",
    "TimeoutSeconds": 8,
    "FailClosed": true,
    "FrameworkVersion": "4.43",
    "ApiKey": "(Bearer token if the core requires it)",
    "LogHealingAttempts": true
  }
}
  • SelfHealing:Provider is the switch: Qhare, Healenium, or Off.
  • Qhare:Enabled must also be true, or the resolver treats QHARE as off.
  • TestConfiguration maps those keys into QhareConfiguration.
  • ConfigurationValidator requires a valid absolute Qhare:BaseUrl when the provider is Qhare.
  • If the BaseUrl key is missing, the code default is http://localhost:8000.

2. Resolve which healer is active

SelfHealingProviderResolver (src/QualiFrame.Framework/Configuration/SelfHealingProvider.cs) is the gate:

  1. Empty provider → legacy fallback: Healenium if Healenium:Enabled.
  2. Off / None / Disabled → no wrapper.
  3. Qhare / QHARE → QHARE only if Qhare:Enabled is true.
  4. Healenium → Healenium only if Healenium:Enabled is true.
Both JSON blocks can have "Enabled": true. The factory still wraps one driver. That is the exclusive-provider rule.

3. Bind a per-scenario healing scope (before the browser)

[BeforeScenario] in src/QualiFrame.Tests/Hooks/Hooks.cs binds an AsyncLocal scope before the driver is created:

  • TestId = scenario title
  • ExecutionId = new GUID
  • Feature = feature title

That scope is how later heal requests know which test and step they belong to. [BeforeStep] calls BeginStep(step text), which clears per-step caches (healed locators, failed locators, pending telemetry).

4. Wrap the real WebDriver at create time

[BeforeScenario] then calls EnhancedWebDriverFactory.CreateDriver() and SetCurrentDriver(driver).

After Chrome / Firefox / Edge (or a cloud driver) is created: 

var healer = SelfHealingProviderResolver.Resolve(_config);
if (healer == SelfHealingProvider.Qhare)
{
    Logger.Information("Wrapping WebDriver with QHARE self-healing wrapper");
    driver = new QhareDriverWrapper(driver, _config.GetQhareConfiguration());
}

File: src/QualiFrame.Framework/Utilities/WebDriver/EnhancedWebDriverFactory.cs

QhareDriverWrapper is an IWebDriver facade around the real driver. Construction:

  1. Builds a QhareClient (HTTP to Qhare:BaseUrl, Bearer ApiKey if set).
  2. Calls QhareHealingContext.AttachClient(_client) so the scenario scope can flush telemetry later.
  3. Logs core URL, project id, and mode.
Page objects never see this. BasePage.Driver is EnhancedWebDriverFactory.GetDriver(), which is already the wrapper.

5. Native find first; heal only on a miss

A typical call is:

BasePage.FindElement(By)
  → WebDriverWait / ExpectedConditions
  → wrapped IWebDriver.FindElement

QhareDriverWrapper.FindElement then:

  1. Calls _baseDriver.FindElement(locator) (real Selenium).
  2. On success, returns immediately. QHARE is not involved.
  3. On NoSuchElementException, enters TryHeal.

Same idea for empty FindElements.

Guards before calling core

  • Qhare:Enabled false or Mode = OFF → rethrow the original miss.
  • Locator already in this step’s FailedLocators → skip (no retry storm).
  • Locator already in HealedLocators → reuse the healed By without another HTTP call.

6. Ask QHARE core to heal

On a real miss, the wrapper:

  1. Temporarily sets implicit wait to zero so healing retries do not sit on the implicit timeout.
  2. Loads the project manifest once: GET api/v1/projects/{ProjectId}/manifest?framework=selenium (locator strategy order, e.g. id → css → xpath).
  3. Posts POST api/v1/heal with project / execution / tenant, framework metadata, test id + current step, original locator, logical name, fingerprint, page URL/title, truncated DOM (max 250k chars), action: find, and mode from config.

Only status HEALED replaces the locator. QhareLocatorPicker maps the candidate onto a Selenium By using the manifest strategy order.

Then it finds the healed locator on the real driver and checks Displayed:

Outcome What happens
Displayed Return the element. Cache healed By for this step. Queue heal.validated.
Found but not displayed Queue heal.rejected, remember as failed, rethrow original NoSuchElementException.
SUGGESTED / UNRESOLVED / anything else Do not swap the locator. Try recovery (next step).
If core is down and FailClosed is true (the default), the original miss is rethrown. Tests fail closed instead of inventing a locator.

7. Optional recover path

If the heal was not HEALED, TryRecover posts POST api/v1/recover. If status is RECOVERED, it runs suggested actions (wait, press_escape, navigate_back, click) and retries the original locator.

Success queues heal.validated with policy RECOVERED_THEN_ORIGINAL. Failure is ignored and the original miss is thrown.

8. Flush telemetry after the Reqnroll step

Heals are not sent immediately. They are queued on the scenario scope.

[AfterStep] calls QhareHealingContext.CommitBoundStep(stepPassed):

  • heal.validated is sent only if the step passed.
  • heal.failed / heal.rejected are sent even if the step failed.

Flush goes to POST api/v1/telemetry/events. [AfterScenario] unbinds the scope.

A healed locator that then causes a failing assertion is not reported as a validated heal.
